## High-Level Goal

Ship a stable `particles.collisions.mode = "fluid"` behavior that:

- uses DDR-based neighborhood resolution (correct `q` factor + velocity reconstruction)
- remains mutually exclusive with `bounce` / `absorb` / `destroy`
- requires no new plugin package or loader
- preserves backward compatibility for existing collision modes

and add a deterministic `generate_code` MCP tool that:

- turns a natural language description into complete, ready-to-use code
- favors specialized bundles (`@tsparticles/confetti`, `@tsparticles/fireworks`, etc.)
- stays a pure function (no filesystem I/O, no network, no LLM dependency)

## Feature A — Fluid as Collision Mode

### Phase 0 — Baseline and guardrails

1. Validate current collisions package build + tests baseline
2. Record current behavior of `bounce`, `absorb`, `destroy` for regression reference
3. Confirm planning docs no longer depend on standalone fluid package

Exit criteria:

- baseline green
- migration target clear (`collisions.mode = "fluid"`)

### Phase 1 — Contract extension (types + options)

1. Add `fluid` to `CollisionMode`
2. Add `ICollisionsFluid` interface and `CollisionsFluid` class with defaults/load
3. Wire `collisions.fluid` loading in collisions options class
4. Ensure defaults are present and safe

Exit criteria:

- options parse correctly
- type surface compiles

### Phase 2 — Runtime implementation

1. Extend collision particle runtime with fluid transient state (incl. `prevPos`)
2. Implement pre-advection snapshot in `Collider.reset()` for fluid-mode particles
3. Implement fluid DDR branch in `Collider.interact()`:
   - density and near-density accumulation
   - pressure computation
   - soft boundary spring + hard boundary clamp
   - symmetric displacement (`dir * q * (P + Pnear * q) * 0.5`)
   - velocity reconstruction from `prevPos`
4. Keep classic collision branch untouched

Exit criteria:

- fluid mode runs without NaN/Infinity
- classic modes behavior unchanged by branch isolation

### Phase 3 — Stabilization and tuning

1. Validate behavior on representative configs (baseline/soft/dense)
2. Verify no mixed-mode artifacts
3. Add guards/clamps/neighbor caps
4. Check performance characteristics with medium/high particle counts

Exit criteria:

- stable visual behavior (cohesive pooling with gravity)
- acceptable performance profile, no hot-loop allocations

### Phase 4 — Documentation and release readiness

1. Update collisions markdown docs (`mode` table + `collisions.fluid` options)
2. Ensure release notes describe fluid as collisions extension
3. Verify no docs mention a standalone fluid package/loader as an active path

Exit criteria:

- docs coherent with implementation
- release notes aligned with product decision

## Risks and Mitigation

### Risk 1 (Fluid): classic mode regression

Mitigation:

- strict mode branching
- targeted regression tests for `bounce`, `absorb`, `destroy`

### Risk 2 (Fluid): fluid instability (jitter/explosion)

Mitigation:

- enforce formula correctness (`dir * q * (P + Pnear * q) * 0.5`)
- force clamp, distance epsilon guards
- velocity reconstruction from `prevPos`
- conservative defaults

### Risk 3 (Fluid): boundary artifacts

Mitigation:

- soft spring + hard clamp sequence in fluid branch
- documented recommendation for `move.outModes`

### Risk 4 (Fluid): performance drop on dense scenes

Mitigation:

- neighbor cap
- grid-based queries
- avoid hot-loop allocations

### Risk 5 (MCP): free-form descriptions produce unusable output

Mitigation:

- deterministic keyword matching with priority-ordered bundles
- framework-specific templates with overrides
- comprehensive bundle/options/codegen tests

## Rollback Strategy

### Fluid

1. Keep enum/options behind internal state or revert fluid additions
2. Ship 4.5.0 without fluid mode if stability/performance criteria are unmet
3. Preserve the fluid-as-collisions-mode architectural decision for next iteration

### MCP `generate_code`

1. Keep the tool behind the existing `src/tools/` structure; it is additive-only
2. If codegen quality is inadequate, do not expose it in MCP `ListTools` and fix in follow-up
